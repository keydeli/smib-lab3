# Учебный репозиторий документации СМИБ

Автор лабораторной работы: Илья Трубников.

## Назначение

Репозиторий создан для лабораторной работы № 3:
«Ведение документации системы менеджмента информационной безопасности
в системе контроля версий».

Все документы относятся к вымышленной организации «Учебная организация».
Репозиторий не содержит документации работодателя, персональных данных
клиентов, паролей или других конфиденциальных сведений.

## Структура

- 01-politika — политика информационной безопасности верхнего уровня.
- 02-chastnye-politiki — частные политики.
- 03-procedury — процедуры и регламенты.
- 04-instrukcii — инструкции, шаблоны и чек-листы.
- 05-zapisi — шаблоны записей, подтверждающих выполнение процессов.

Первые четыре каталога отражают четырёхуровневую иерархию документации.
Каталог 05-zapisi выделен отдельно для шаблонов записей.
Файлы .gitkeep обеспечивают сохранение пустых каталогов в Git.

## Область действия учебной СМИБ

СМИБ охватывает сотрудников, учебную информационную систему,
рабочие станции, учётные записи, электронные документы и процессы
обработки информации вымышленной организации «Учебная организация».

Это описание является областью действия СМИБ для данной лабораторной работы.

## Порядок внесения изменений

1. Получить актуальное состояние основной ветки main.
2. Создать отдельную ветку с осмысленным именем.
3. Изменить документ и при необходимости его реквизиты.
4. Создать коммит с описанием изменения и его причины.
5. Отправить рабочую ветку в GitHub.
6. Создать Pull Request в main.
7. Назначить другого обучающегося рецензентом.
8. Получить замечания и устранить их отдельными коммитами.
9. Получить одобрение рецензента и завершить обсуждения.
10. Выполнить слияние через GitHub.
11. Пометить принятую редакцию аннотированным тегом.
12. Сохранить доказательства проверки и изменения для отчёта.

После первоначального размещения структуры ветка main защищается.
Прямая отправка изменений в защищённую main, принудительная запись
и удаление ветки не допускаются.

## Учебное согласование и утверждение

Рецензент выполняет анализ документа на пригодность и адекватность.
Одобрение Pull Request используется как запись учебного согласования.
Автор после одобрения выполняет слияние и присваивает тег редакции.

В реальной организации полномочия на утверждение должны быть назначены
организационно. Одобрение одногруппника не является утверждением
реальной политики руководством организации.

Дата утверждения в учебной политике относится к дате одобрения
соответствующего Pull Request. До одобрения документ имеет статус проекта.
Если согласование переносится на другой день, дата корректируется
до окончательного одобрения.

## Идентификация редакций

- v1.0 — первоначальная учебная редакция политики после проверки.
- v1.1 — редакция после изменения порядка пересмотра и проверки.

Действующая учебная редакция определяется последним принятым тегом
и соответствующей записью одобрения Pull Request.
Тег сам по себе не подтверждает наличие утверждения.

## Ограничения

Git обеспечивает историю версий, но сам по себе не обеспечивает:
- утверждение уполномоченным руководителем;
- гарантированную доступность и резервное восстановление;
- сроки хранения и полное уничтожение всех копий;
- соблюдение правил использования документов вне репозитория.

Для этого необходимы организационные правила, резервное копирование,
управление полномочиями и контроль распространённых копий.
